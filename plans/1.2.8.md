# Veyra 1.2.8 — Upload Limits, Queue Reliability, Profile Customization, Dual-Database Strategy & Scale

Release theme: close the remaining reliability gaps in the write path (upload limits, EZMSG write-behind, realtime fan-out), ship the next profile/social customization layer, decide and document the primary/backup database story, and prove the architecture under concurrent load.

Current version: `1.2.7` (`package.json`). This plan targets `1.2.8`.

---

## 0. Goals

1. **Prove scalability** — measure, don't assume. Define load targets and verify them with a repeatable load test.
2. **Improve fault tolerance** — transient failures must retry, not dead-letter; crashes must not lose or duplicate messages.
3. **Handle concurrent users** — distinguish "online" from "actively sending" from "receiving realtime" and size each path independently.
4. **Deepen profiles** — add social links, richer presence modes, interests/languages, QR-based friend adding, animated profile media, profile music, and customizable profile layout without turning profiles into a media-hosting problem.

Concurrency targets to prove (in order of difficulty):

- 100 users online (idle presence).
- 100 users actively sending messages (not necessarily simultaneous).
- 100 users sending messages **simultaneously** (burst).
- 1,000 users receiving realtime updates generated by those messages.

## Finding 1: Upload limit discrepancy — code enforces 25 MB, buckets allow more

**Status: confirmed.**

`MAX_CHAT_UPLOAD_BYTES = 25 * 1024 * 1024` in `server/app.mjs` applies to **all** chat buckets, and `src/lib/uploadLimits.ts` (`MAX_UPLOAD_SIZE_BYTES = 25 MB`) applies the same cap client-side for every file type.

Supabase bucket limits as configured:

| Bucket | Bucket limit | API/client cap | Gap |
| --- | --- | --- | --- |
| `avatars` | 25 MB | 25 MB (`MAX_PROFILE_IMAGE_BYTES`, profile endpoint only allows JPEG/GIF) | none |
| `banners` | 25 MB | 25 MB | none |
| `chat-images` | 50 MB | 25 MB | users can't use half the bucket |
| `chat-videos` | 50 MB | 25 MB | users can't use half the bucket |
| `chat-voice` | 45 MB | 25 MB | voice notes truncated well under bucket cap |

So the API is the bottleneck, not the buckets. Two valid directions — pick one:

- **Option A (recommended): per-bucket limits.** Replace the single `MAX_CHAT_UPLOAD_BYTES` with a `bucket → maxBytes` map in `server/app.mjs` matching the bucket config (`chat-images`/`chat-videos` 50 MB, `chat-voice` 45 MB), and split `uploadLimits.ts` into per-kind constants so the client validates against the right cap per file type. Keep a hard global ceiling (e.g. 50 MB) regardless of bucket.
- **Option B: shrink buckets to 25 MB.** Change Supabase bucket file-size limits to 25 MB and keep code as-is. Simpler, but voice notes and videos lose headroom.

Either way the frontend constant and the API constant must move together — changing only one side produces either client-side rejects of valid uploads or API `413`s on files the UI allowed.

**Additional check during implementation:** verify the actual upload path still enforces size server-side at Supabase (signed upload URL doesn't enforce size by itself — the bucket limit does). Confirm `imageCompress.ts` output stays under the image cap so the common case never hits the limit.

**Work:**
- [ ] Decide Option A vs B.
- [ ] If A: `CHAT_UPLOAD_LIMITS` map in `server/app.mjs`; per-kind limits in `src/lib/uploadLimits.ts`; update `ChatView.tsx` call sites (they currently use one shared `exceedsMaxUploadSize`).
- [ ] If B: update bucket limits in Supabase dashboard + document in `docs/`.
- [ ] Update error strings (currently hardcoded "25 MB" at `server/app.mjs` lines ~287, ~329) to use the per-bucket value.
- [ ] Regression: upload a 30 MB voice note and a 30 MB video — both should succeed under Option A, both `413` under Option B.

## Finding 2: EZMSG write-behind dead-letters on transient DB errors

**Status: confirmed.** `server/data.mjs` `drainEzmsgQueue()` → on any insert error it calls `ezmsgMarkFailed(item, error)` then `ezmsgAck(raw)` (lines ~526-530). A temporary MariaDB outage moves every drained item straight to the dead-letter list `veyra:v1:ezmsg:failed` — no retry.

**Work:**
- [ ] Add an `attempts` counter (and `lastError`) to the queued item payload.
- [ ] Classify errors: **permanent** (constraint violations, bad payload, unknown table) → `ezmsgMarkFailed` immediately; **transient** (connection errors, deadlocks `ER_LOCK_DEADLOCK`, pool exhaustion, timeouts) → requeue.
- [ ] Requeue strategy: keep the item in the processing list and retry on the next drain tick with exponential backoff (e.g. 1s → 2s → 5s → 15s → 60s cap), OR `LPUSH` back onto the queue with a per-item `notBefore` timestamp the drain respects. Max attempts (e.g. 8) → dead-letter.
- [ ] Surface queue depth + dead-letter count: expose in the admin dashboard or a `/api/health`-adjacent diagnostic so a stuck drain is visible.
- [ ] Add a test in `server/redis.test.mjs` or a new `server/data` test covering: transient error retries, permanent error dead-letters, crash-recovery doesn't lose items.
- [ ] Update `docs/redis.md` and `Releases.md`.

## Finding 3: EZMSG insert is not idempotent — duplicates land in failed list

**Status: confirmed.** `insertQueuedRow()` (`server/data.mjs` ~line 483) issues a plain `INSERT INTO`. Message IDs are client-generated UUIDs, so a retry after a crash-between-insert-and-ack hits a duplicate-key error → treated as failure → dead-lettered, even though the row is already persisted.

**Work:**
- [ ] Make the queued insert idempotent on `id`. Options:
  - Catch `ER_DUP_ENTRY` specifically and treat as success (verify the existing row matches, then ack). Works on both dialects since `db.mjs` already normalizes PG `23505` → `ER_DUP_ENTRY`.
  - Or `INSERT ... ON DUPLICATE KEY UPDATE id = id` (MySQL) / `ON CONFLICT (id) DO NOTHING` (Postgres) — `translateSql` already supports both `INSERT IGNORE` and upsert translation; prefer whichever reads cleanest. Note: `INSERT IGNORE` in MySQL downgrades *some* data errors to warnings, so prefer explicit dup-key handling or `ON DUPLICATE KEY UPDATE` over `INSERT IGNORE`.
- [ ] After a dup-key "success", still run the realtime publish + notification path? Decide: the first successful insert already published; a recovered duplicate should ack **without** re-publishing (check `insertId`/affected rows or a pre-`SELECT`).
- [ ] Add an `idempotency_key`/attempt-token to the queue item so operators can trace a message through queue → DB.
- [ ] Regression test: simulate insert-success-then-crash (item recovered, second drain attempt) → row exists once, item acked, no failed-list entry, no duplicate realtime event.

## Finding 4: No primary/backup database replication exists

**Status: confirmed.** `server/db.mjs` selects **either** MariaDB (`USE_MARIADB` unset/true) **or** PostgreSQL (`USE_MARIADB=false`) via `translateSql`/`bindParams`. There is no dual-write, no logical replication, no CDC. Setting both `MARIADB_*` and `POSTGRES_*` env vars does nothing — only one pool is created.

If the deployment plan is "PostgreSQL primary, MariaDB as backup" (or vice versa), that mechanism must be built or bought. Options, in rough order of effort:

- **Option A — independent environments + cutover tooling (lowest effort).** Keep the dialect switch; use `server/migrate-to-postgres.mjs` for planned migrations. No live replica; backups are per-database dumps (`mysqldump`/`pg_dump` + WAL archiving or `pgBackRest`). Acceptable if RPO/RTO of "planned migration + independent backups" is fine.
- **Option B — dual-write shim in `db.mjs`.** Route every write to both pools, read from primary. Hard problems: encrypted message fields (`server/encryption.mjs` AES-256-GCM) must encrypt **once** and write identical ciphertext to both; sequences/IDs are client-generated UUIDs so no sequence sync needed; conflict resolution undefined if one side is written directly; doubles write latency and pool pressure. Only viable if both DBs are truly symmetric — they are not (different schemas: `schema.sql` vs `schema.postgres.sql`).
- **Option C — CDC replication.** Debezium/Postgres logical decoding → MariaDB is not a supported target; realistically you'd replicate Postgres→Postgres or use a managed mirror. MariaDB→Postgres similarly needs custom ETL. This is the only true "live replica" path and it's the most infrastructure.
- **Option D — managed backups.** Supabase/Neon/Layerbase point-in-time recovery + MariaDB host snapshots. Cheapest real "backup" if the goal is disaster recovery, not a queryable replica.

**Recommendation to decide in this release:** state the actual requirement (queryable replica vs DR backup vs migration path), pick A or D for 1.2.8, and defer B/C unless truly needed. Whichever is chosen:

- [ ] Document the decision + runbook in `docs/postgres.md` (or a new `docs/database-replication.md`).
- [ ] If backups: add scheduled `pg_dump`/snapshot automation + a documented restore drill. Verify `schema.postgres.sql` restores cleanly.
- [ ] If dual-write is ever pursued: it must live behind the `pool` abstraction in `db.mjs`, encrypt once in `data.mjs` before fan-out, and be covered by tests — do **not** scatter second-pool calls through `server/*.mjs`.
- [ ] Confirm encryption interacts sanely: ciphertext is portable across dialects (it's just bytes in a column), so replication of `messages`/`global_messages`/`announcement_messages` content is fine — but any plaintext-only secondary index/reporting replica would see ciphertext.

## Finding 5 (new): EZMSG queue drains LIFO, not FIFO

**Status: confirmed — ordering bug found during inspection.**

`ezmsgPush` uses `RPUSH` (`server/redis.mjs` line ~203) and `ezmsgPop` uses `RPOPLPUSH` (line ~215). `RPUSH` appends to the tail and `RPOPLPUSH` pops from the tail → the queue behaves as a **stack**: the most recently enqueued message drains first. Under `REDIS_EZMSG=true`, rapid consecutive sends can persist out of order (created_at still sorts correctly on read, but realtime publish order and `mergeQueuedSelect` ordering can invert, and notification fan-out order scrambles).

**Work:**
- [ ] Switch to FIFO: `LPUSH` on enqueue + keep `RPOPLPUSH` (pops tail = oldest), or move the whole queue to a Redis Stream (`XADD`/`XREADGROUP`) consistent with the existing `veyra:v1:realtime-outbox` stream pattern.
- [ ] Keep `ezmsgRecover` semantics correct for whichever structure is chosen (recover un-acked processing items back to the **head** of the pending side, preserving original order).
- [ ] Test: enqueue A then B, drain → A persists before B.

## Finding 6 (new): single-drain, single-process assumptions

EZMSG is disabled on Vercel (`EZMSG_ENABLED = REDIS_EZMSG === 'true' && !VERCEL`), so the drain worker only runs on the self-hosted Node server. Today that's one process. If the Node server ever runs >1 replica:

- [ ] `drainEzmsgQueue`'s `ezmsgDraining` flag is per-process; two replicas would race on `RPOPLPUSH`. `RPOPLPUSH` itself is atomic so no item is lost, but both replicas could drain concurrently — actually fine for throughput, but `ezmsgRecover` is **not** safe concurrently: two processes could both `lRange` + `rPush` + `del` the processing list, duplicating items (mitigated by Finding 3's idempotent insert — another reason to fix it first).
- [ ] Decide: either document "single Node replica only" for EZMSG, or add a Redis lock (`SET NX PX`) around `ezmsgRecover`.

## Feature scope (new): Profile customization & social discovery

**Status: requested for 1.2.8 — needs schema, API, privacy, and UI work.**

Requested features:

- Social/profile links.
- Manual status modes: `online`, `idle`, `do_not_disturb`.
- Interests/tags.
- Languages spoken.
- Profile QR code in Settings + QR scan-to-add flow.
- Animated profile media: GIF/video banners/profile media, max 5 seconds.
- Profile song player.
- Custom profile layout/section ordering.

### Proposed data model

- **`profile_links` table** — `id`, `user_id`, `label`, `url`, `position`, `created_at`; owner-only writes, public reads. Validate `https?://` URLs, cap label/url length, cap link count, and render sanitized links in `UserProfileDialog`.
- **`profiles.status_mode`** — `ENUM('online','idle','do_not_disturb')` in MariaDB and `VARCHAR` + `CHECK` in PostgreSQL, default `online`. Presence/chat UI should read this mode; decide whether `idle` is manual-only or auto-set after inactivity, and whether `do_not_disturb` suppresses desktop/mobile notifications while still showing online presence.
- **`profiles.interests` / `profiles.languages_spoken`** — JSON arrays is probably enough for v1: interests as short lowercase tags (max ~10), languages as `{ code, label }` entries (max ~10). Normalize/dedupe server-side.
- **`profiles.profile_song`** — JSON object `{ title, artist, url, artwork_url? }` for a single track. Restrict `url` to HTTPS audio or Veyra storage media; no arbitrary iframe/embed HTML.
- **`profiles.profile_layout`** — JSON array of whitelisted section keys + visibility/order, e.g. `bio`, `links`, `interests`, `languages`, `song`, `custom_status`, `badges`. Server validates against an allowlist; clients fall back to the default layout for unknown keys.
- **Animated profile media** — extend existing banner/avatar media handling with a media kind (`image`/`gif`/`video`) and duration metadata instead of adding a separate table. Enforce GIF/video max duration of 5s, muted autoplay, poster fallback, and reduced-motion support.
- **QR friend codes** — new `profile_friend_codes` table or equivalent: one active revocable code per user, `code_hash`, `auto_accept`, `created_at`, `revoked_at`. QR payload should encode a profile URL/deep link plus the friend code, e.g. `veyra://user/<username>?friend=<code>` and a web fallback `/u/<username>?friend=<code>`.

### QR friend flow

- Settings shows the current user's QR code with username/avatar and a regenerate/revoke control.
- Scanning a QR opens the profile/add-friend flow directly — no username search required.
- Two modes:
  - **QR request mode:** scanner sends a normal pending `friend_requests` row tagged as QR-originated. Fast, but still requires acceptance.
  - **QR auto-accept mode:** explicit opt-in privacy setting (`auto_accept`) allows a valid scanned code to create an accepted friendship directly. Because QR images are shareable bearer credentials, auto-accept must be off by default, revocable/regenerable, rate-limited, and audited enough to investigate abuse.
- Do not auto-create a DM unless the existing friend-accept path intentionally does so; friend add and DM creation should remain separate concerns.

### UX surfaces

- `Settings` → Profile: social links editor, interests, languages, status mode, song config, layout editor, animated media upload, QR card.
- `PrivacySettings`: QR auto-accept toggle + friend-code regenerate/revoke.
- `UserProfileDialog`: render links, interests, languages, song player, badges, and sections in the user's custom order.
- Chat/friends lists: show `status_mode` alongside presence/custom status.

### Privacy/security requirements

- Social links, interests, languages, song, and layout are public profile fields unless a later privacy toggle says otherwise.
- QR auto-accept is opt-in only; codes are revocable and rate-limited.
- Animated media must respect upload caps from Finding 1, max 5s duration, safe MIME allowlist, and storage cleanup for expired/unused objects.
- Profile layout must be a whitelist-driven JSON config — never raw HTML/CSS.
- Profile song URLs must be HTTPS-only and sanitized; prefer Veyra Storage for uploaded audio.

## Scalability & concurrency workstream

### What already exists (verified in code)

- **Redis shared rate limits** — atomic Lua `INCR`+`PEXPIRE` (`server/redis.mjs` `consumeRateLimit`), 600 req/min per user on `/api/data`, 120/min on chat-upload; in-memory fallback per instance.
- **Request coalescing** — `coalesce()` caps in-flight duplicate reads at `MAX_IN_FLIGHT = 500`.
- **Read cache** — Redis `veyra:v1:read:*` with per-table epoch invalidation, 2s TTL, 256 KB value cap.
- **DB pool** — mysql2/pg pool, `connectionLimit` capped at **2 per instance** (deliberate: Vercel × Altare/Layerbase ~20-client cap). `queueLimit: 50` on MySQL side.
- **Realtime fan-out control** — conversation-scoped HMAC topics (`veyra-conv-*`) for `messages`/`reactions`/`polls`; per-user topics capped at 1,000 recipients; member lists cached 20s in Redis; broadcast POST has 1.5s timeout.
- **Realtime outbox** — failed broadcasts go to `veyra:v1:realtime-outbox` stream (MAXLEN ~10k), drained on subsequent publishes (up to 50 batches).
- **Write-behind** — EZMSG queue (see findings above; off by default).
- **Client-side resilience** — `chatCache.ts` localStorage history (24h TTL), message reconciliation/dedup, resync on realtime reconnect.
- **Bounded writes** — bulk insert/update/delete capped at 200 rows; filter/`in`/`OR` clause sizes bounded; message content ≤8000 chars.
- **Signed-URL caching** — `/api/storage/chat-read` caches signed URLs in Redis for 50 min, batches up to 50 items.

### Known ceilings / gaps to address

- **Pool size 2/instance.** With N warm Vercel instances that's 2N connections — fine vs a 20-client cap only if N≤10. If Altare MariaDB allows more, raise `MARIADB_POOL_SIZE`/`POSTGRES_POOL_SIZE` deliberately and document the math. For self-hosted (non-Vercel) Node, the cap of 2 is unnecessarily tight — consider a higher default when `VERCEL` is unset.
- **Realtime broadcast is one HTTP POST per publish call** with a 1.5s timeout. Under a 100-sender burst, publishes are sequential per request; Supabase Realtime broadcast rate limits are unverified — load test must confirm.
- **Per-user topic fan-out** still exists for non-conversation tables (friend requests, profiles, roles, membership). A viral profile update could fan out to many users — the 1,000-user slice cap silently drops recipients beyond that; verify acceptable.
- **No metrics.** There is no latency histogram, pool-wait timing, Redis hit-rate, or queue-depth telemetry. Fault tolerance claims need observability first.
- **Single Node process** for self-hosted; no clustering story (EZMSG timers, in-memory rate-limit fallback, local rate buckets are all per-process).

### Work items

- [ ] **Instrumentation (do first):** add lightweight timing — per-route p50/p95, DB pool acquire wait, Redis hit/miss, EZMSG queue depth + failed count, realtime broadcast success/failure. Structured logs or a `/api/metrics`-style endpoint (internal-only).
- [ ] **Load test harness:** k6 or Artillery script in `scripts/` (e.g. `scripts/load-test.js`) covering: N concurrent `/api/auth/login` + message sends + history reads + realtime subscribers (Realtime is websocket — may need a small Node script using the Supabase client). Parameterize N; run against staging.
- [ ] **Run the ladder:** 100 online → 100 active senders → 100 simultaneous senders → 1,000 realtime receivers. Record p50/p95/p99 for send, history fetch, and realtime delivery latency.
- [ ] **Fix what the numbers show.** Likely candidates: raise pool size where the DB allows, batch realtime publishes, tune EZMSG drain budget, add DB indexes if `EXPLAIN` shows scans on hot paths (`messages(conversation_id, created_at)` already exists — verify others).
- [ ] **Document capacity envelope** in `docs/` or `README.md`: "tested to X concurrent senders / Y realtime subscribers on <infra>".
- [ ] **Chaos checks:** kill Redis mid-load (should fall back to direct DB writes + local rate limits), kill MariaDB briefly during EZMSG drain (Finding 2 retry path), restart Node mid-drain (Finding 3 idempotency).

## Suggested order

1. **Finding 3 + Finding 5** (EZMSG idempotency + FIFO) — small, unblocks safe enablement of `REDIS_EZMSG`.
2. **Finding 2** (retry/dead-letter classification) — depends on 1 for correctness.
3. **Finding 1** (upload limits) — independent; needs a product decision (Option A vs B). Animated profile media depends on the final per-bucket limits.

5. **Instrumentation + load test** — needed before tuning anything else.
6. **Finding 4** (DB strategy decision + docs/runbook) — decision first, implementation only if Option B/C chosen.
7. **Scale fixes** driven by load-test results.

Each item ships with `database/schema.sql` + `database/schema.postgres.sql` updates where schema changes (Finding 4 Option B may need none; EZMSG changes are Redis-only; profile customization definitely needs both schemas), docs updates per AGENTS.md, and `npm run lint` / `npm test` / `npm run build` verification.
