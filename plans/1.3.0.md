# Veyra 1.3.0 — Discord-Style Servers, Friends & UI Overhaul

**Status:** Proposed
**Version:** 1.3.0
**Previous Version:** 1.2.5

## Overview

Veyra 1.3.0 transforms Veyra's chat surface into a Discord-style experience:

1. **Fix the friend/group-chat bugs** — friends missing from group/member pickers, fragile friend-request handling.
2. **Rebuild the friends system** — a real friends list (online/all/pending/blocked/add-friend) instead of "DM conversations == friends".
3. **Add Servers** — user-created communities with categories, text channels, roles, permissions, and invite links (Discord model).
4. **Discord-like UI everywhere** — server rail, channel sidebar, member list, grouped messages, dark theme — on web, desktop (Electron), and Android (Capacitor).
5. **Rich icons** — PNG/JPEG/GIF/WebP/AVIF for avatars, banners, group icons, and server icons.
6. **Docs** — update `AGENTS.md`, `README.md`, `Releases.md`, `docs/*`, `.env.example` in the same change (required by AGENTS.md).

This is a large release. Every section lists concrete files, schema changes, and verification steps. Answer the open questions in §10 before implementing.

## 0. Research summary — the Discord model we're copying

### Layout (desktop)

Three columns:

- **Server rail** (~72 px, `#1e1f22`): home/DM button, server icons (rounded-square → circle on hover/active, left-edge pill indicator, mention badge), "+" add-server, "explore", user panel at bottom.
- **Channel sidebar** (~240 px, `#2b2d31`): server header (name + dropdown: Invite, Server Settings, Create Channel, Notification Settings, Leave), collapsible **categories** → **text channels** (`#`) / **voice channels**, user panel at bottom.
- **Chat** (`#313338`): channel header (`# name`, topic, member-list toggle, search), message list, member list (~240 px, right, grouped by role).

### Concepts to mirror

- **Servers:** anyone can create one free. Owner + members + roles + categories→channels + invites.
- **Roles & permissions (exact Discord algorithm):**
  - Every member has `@everyone` (position 0) plus assigned roles. Final permissions = sum of all role allows, then apply channel overwrites in order: `@everyone` deny → `@everyone` allow → all role denies (summed) → all role allows (summed) → member-specific deny → member-specific allow. **An allow anywhere beats denies at the same level; channel overwrites beat server-wide role permissions.**
  - `ADMINISTRATOR`-equivalent bypasses everything.
  - **Hierarchy:** you can only assign/edit/reorder roles *below* your highest role, only grant permissions you yourself have, and can only kick/ban/nick members whose highest role is below yours. Role *order does not* decide permissions — only these moderation limits.
- **Channels:** text channels hold messages; per-channel permission overwrites per role/member; categories group channels and can carry default overwrites; channel flags: topic, slow mode (seconds between messages per member), read-only/announcement.
- **Invites:** revocable codes/links with optional expiry and max uses.
- **Friends:** separate from servers. Tabs: **Online / All / Pending / Blocked / Add Friend**. Add by username; incoming+outgoing pending; block list; custom status/rich presence.
- **DMs & Group DMs:** 1:1 and group DMs (Discord cap: 10 members) share the Messages view, fully separate from servers. **Any member can add friends to a group DM**; group DMs have a name/avatar/member list and *no owner role*.
- **Mentions:** `@user`, `@role`, `@everyone`, `@here`, `#channel` — rendered as colored pills, not plain text.
- **Message list:** consecutive messages from the same author within ~7 minutes collapse into a compact group (avatar/name/timestamp only on the group head); hover reveals react/reply/edit/delete/more.
- **Deferred (explicitly out of scope):** voice channels, stage channels, forum channels, threads, server discovery/explore, Nitro boosts, scheduled events, message requests (Veyra requires friendship for DMs anyway).

Veyra already has ~70% of the messaging primitives (messages, reactions, replies, polls, pins, receipts, media, presence/typing, per-conversation mute). The work is: canonical friends graph, the server container model, and the visual/structural overhaul.

## 1. Bug: friends missing when creating a group chat / adding members

**Reported:** creating a group chat shows only 2 of 4 friends.

### Confirmed code facts

- `CreateGroupDialog.tsx` builds its picker from `friend_requests` rows with `status='accepted'` involving the user, then batch-loads `profiles`.
- **`GroupSettingsDialog.tsx:~176-197` has the same pattern** — the "add members" picker also queries `friend_requests` directly, so the same missing-friends bug exists when adding members to an existing group.
- The sidebar "friends" come from `get_user_dm_list` (`server/rpc.mjs:41`), which returns **every 1:1 `conversations` row regardless of friendship state** — so "4 friends" in the UI can be 4 DM conversations while only 2 are real friendships.
- `friend_requests` has a **directional** unique key `(sender_id, receiver_id)`: both directions can coexist with different statuses (A→B `accepted`, B→A stuck `pending`). The picker dedupes by id so this alone shouldn't drop friends, but it makes the graph ambiguous.
- `parseOr()` in `server/data.mjs:209` splits `.or()` on `,` and supports only flat `col.op.value` — it **cannot parse nested `and(...)`**. `FriendsList.unfriend()` sends `.or("and(sender_id.eq.X,receiver_id.eq.Y),and(...)")` → fragments fail the regex → delete errors. **`UserProfileDialog.removeFriendship()` likely uses the same broken pattern — audit it.** If confirmed, unfriending is broken and "removed" friends never leave.
- `MariaQuery.or()` **overwrites** `payload.or` — `sendFriendRequest`'s chained `.or().or()` keeps only the last clause.
- `fetchUpsertedFriendRequests` (`data.mjs:488`) fetches by `(sender_id, receiver_id)` pairs — fine, but will need updating if pair normalization lands.

### Work

1. **Reproduce first.** In `npm run dev`, dump the user's `friend_requests` rows (both directions, all statuses) and their 1:1 `conversations`/`conversation_members`. Determine which "friends" lack an `accepted` row, have stale reverse rows, or exist only as conversations.
2. **Canonical friends source.** New RPC `get_friends` in `server/rpc.mjs`: normalized accepted friendships (one row per pair regardless of direction) joined to `profiles`, LEFT JOINed to the DM conversation (via `dm_pairs`) for `conversation_id`, unread count, `last_message_at`, and a `last_message_preview` snippet. Use it for: friends list UI, `CreateGroupDialog`, `GroupSettingsDialog` add-member picker, group-DM picker.
3. **Fix `parseOr`** to support nested `and(...)`/`or(...)`, or simpler: change unfriend/remove-friendship flows to delete by explicit friendship ids (fetch pair rows first, delete by `id IN (...)`). Add a regression test either way.
4. **New `send_friend_request` RPC** — atomic server-side: validates target exists, not self, `allow_friend_requests`, no block either direction, no existing accepted/pending pair; inserts or revives the row; returns resulting state. Replaces the fragile client flow in `FriendsList.sendFriendRequest` and `UserProfileDialog`.
5. **Reconcile DM list vs friends.** Keep `get_user_dm_list` returning conversations, but the sidebar gets a real **Friends** section (from `get_friends`) separate from **Direct Messages**. Non-friend legacy DMs get a "not friends" affordance (Add friend / Remove). Policy decision in §10.
6. **Regression tests:** picker shows exactly the accepted-friend set; unfriend removes the pair AND cleans up per policy; re-adding after unfriend/reject works; `parseOr` nested-clause cases.

## 2. Friends system rebuild (Discord-style)

### Schema

- `friend_requests`: keep the table but normalize to **one row per unordered pair**:
  - Add `user_low CHAR(36)`, `user_high CHAR(36)` + `UNIQUE(user_low, user_high)` (same pattern as `dm_pairs`), backfilled from existing rows.
  - Migration: collapse duplicates keeping precedence `accepted` > `pending` > `rejected`/`cancelled`; repoint nothing else (rows are referenced by id only in UI state).
  - `status` stays `pending|accepted|rejected|cancelled` — `cancelled` = requester withdrew (Discord parity).
- `profiles`: keep `allow_friend_requests` boolean (maps to Discord's "who can add me" — server-side everyone). Optional `friend_request_permission` enum deferred.
- `blocked_users`: unchanged; surfaced in the Blocked tab.
- Presence stays client-side via Supabase Realtime (`useGlobalPresence`); "Last seen" timestamps deferred (presence isn't persisted server-side today).

### Backend (`server/rpc.mjs`, `server/data.mjs`, `server/realtime.mjs`, `server/notifications.mjs`)

- `get_friends(userId)` → rows: `friendship_id`, `user_id`, `username`, `display_name`, `avatar_url`, `status`(custom status fields), `conversation_id` (DM if exists), `unread_count`, `last_message_at`, `last_message_preview` (truncated decrypted content — careful: content is encrypted at rest; compute preview from the decrypted read path or store a plaintext preview column — **decision needed**, see §10; simplest: return last message id+created_at and let the client show "last message" via existing DM list join, or add `messages.preview` plaintext column populated on insert).
- `send_friend_request(other_id)` → atomic; returns `{ status: 'sent' | 'accepted' | 'already_friends' | 'pending_incoming' | ... }`. Rate-limit via `consumeRateLimit` (~20/hour/sender).
- `respond_friend_request(friendship_id or pair, accept)` → accept calls `ensureDirectMessage` once (already atomic via `dm_pairs`); decline sets `rejected`.
- `cancel_friend_request(pair)` → `cancelled`; `unfriend(pair)` → delete row + DM cleanup per §10 decision.
- `block_user`/`unblock_user` RPCs (or keep `blocked_users` table writes — they already work via `canInsert`; verify block also unfriends server-side for consistency with `UserProfileDialog`'s client-orchestrated flow — **move that orchestration into an RPC** so it's atomic).
- `get_friend_suggestions` — skip unless trivial.
- **Realtime:** `friend_requests` events already fan out to sender+receiver (`realtime.mjs:115`). With pair normalization, `keys` still carry `sender_id`/`receiver_id` — verify `collectKeys`/`recipientsFor` still resolve (they read the row by `id` when keys are missing — keep `id` in SAFE_KEYS flow). Add a lightweight `friends_changed` notice or reuse the existing table event so both sides refetch `get_friends`.
- `data.mjs` `policy()`/`canInsert` for `friend_requests`: keep select/delete for participants; **restrict insert/update to the new RPC path** or keep the existing rules working during transition — decide; the RPC path is preferred for correctness (atomic pair checks).

### Frontend — new Friends view

Rework `FriendsList.tsx` (or split into `src/components/friends/`):

- Discord-style tabs with icons + count badges: **Online · All · Pending · Blocked · Add Friend**.
  - *Online:* friends currently in `useGlobalPresence` set, grouped; status text "Online" / custom status.
  - *All:* alphabetical, avatar + status dot (green online / gray offline; idle if we add an idle signal — see §10) + display name + @username + custom status.
  - *Pending:* incoming (Accept/Decline) and outgoing (Cancel) with relative timestamps.
  - *Blocked:* from `blocked_users` + profiles, Unblock action.
  - *Add Friend:* username input → `send_friend_request` → result states (Pending sent / Already friends / Request sent / User not found / Can't add — blocked or privacy).
- Friend row: avatar+status dot, name, @handle, custom status, **Message** button (`get_or_create_dm`), context menu (`context-menu.tsx` exists): Message, View Profile, Pin DM, Remove Friend, Block.
- DM rows keep unread badge + last-message preview + timestamp (Discord style) — merge `get_friends` + `get_user_dm_list` data or extend `get_friends` to cover it (recommended: `get_friends` returns DM fields; `get_user_dm_list` stays for the pure DM list incl. non-friend legacy convos).
- `chatCache`: add `friends:<userId>` and `srv:*` cache keys (envelope is generic — new namespaces only; bump `PREFIX` only if shape changes).

## 3. Servers

### Core design: channels ARE conversations

A server channel reuses `conversations` + `conversation_members` + `messages` + reactions/polls/pins/receipts/media-signing/mutes — nearly everything works unchanged **if** membership is mirrored.

**New column:** `conversations.kind VARCHAR(16) NOT NULL DEFAULT 'dm'` with values `'dm' | 'group' | 'server'` (backfill: `is_group=1 → 'group'`, `is_group=0 → 'dm'`). This single discriminator lets every existing code path branch correctly:

- `get_user_group_list` (`rpc.mjs:65`) — **must exclude `kind='server'`** or every channel floods the Groups sidebar.
- `get_user_dm_list` — unaffected (`is_group=0`).
- `data.mjs canInsert('messages')` — for `kind='server'` conversations, enforce channel permissions (below) instead of the DM block-check.
- `data.mjs canInsert/policy('conversation_members')` — **deny direct client writes for `kind='server'` conversations**; membership is managed only by server RPCs (prevents permission bypass and keeps `server_members` the source of truth).
- `ChatView`/`GroupSettingsDialog`/`FriendsList` — branch on `kind`: server channels get channel header/settings/member list, not group dialogs.
- `conversations.is_group` stays for backward compat (server channels: `is_group=1`, `name` = channel name denormalized for fallback).

### Schema (both `schema.sql` and `schema.postgres.sql`, additive idempotent block like 1.2.5)

```sql
ALTER TABLE conversations ADD COLUMN kind VARCHAR(16) NOT NULL DEFAULT 'dm';
ALTER TABLE conversations ADD COLUMN avatar_url TEXT NULL;   -- group DM icons

servers (
  id CHAR(36) PK, name VARCHAR(100) NOT NULL,
  icon_url TEXT NULL, banner_url TEXT NULL,
  description VARCHAR(500) NULL,
  owner_id CHAR(36) NOT NULL -> profiles(id) ON DELETE CASCADE,
  verification_level VARCHAR(16) NOT NULL DEFAULT 'none',  -- none|low|medium|high
  created_at, updated_at
)

server_roles (
  id CHAR(36) PK, server_id -> servers ON DELETE CASCADE,
  name VARCHAR(100) NOT NULL, color VARCHAR(9) NULL,
  position INT NOT NULL,            -- higher = higher in list; @everyone = 0
  hoist BOOL NOT NULL DEFAULT FALSE,
  mentionable BOOL NOT NULL DEFAULT FALSE,
  is_default BOOL NOT NULL DEFAULT FALSE,   -- exactly one @everyone per server
  permissions JSON NOT NULL,         -- {view_channel, send_messages, ...} — see below
  UNIQUE(server_id, is_default) can't be partial in MySQL — enforce in RPC instead
)

server_members (
  server_id, user_id, role_id CHAR(36) NULL -> server_roles,  -- NULL = @everyone only
  nickname VARCHAR(80) NULL,
  timed_out_until DATETIME(3) NULL,   -- Discord "timeout" — cheap, include if easy
  joined_at, UNIQUE(server_id, user_id)
)

server_categories (
  id PK, server_id, name VARCHAR(100), position INT, created_at
)

server_channels (
  id CHAR(36) PK, server_id -> servers ON DELETE CASCADE,
  conversation_id CHAR(36) NOT NULL UNIQUE -> conversations ON DELETE CASCADE,
  name VARCHAR(100) NOT NULL, type VARCHAR(16) NOT NULL DEFAULT 'text', -- 'voice' deferred
  category_id CHAR(36) NULL -> server_categories ON DELETE SET NULL,
  position INT NOT NULL,
  topic VARCHAR(500) NULL,
  slow_mode_seconds INT NOT NULL DEFAULT 0,
  is_readonly BOOL NOT NULL DEFAULT FALSE,   -- announcement-style channels
  created_at
)

server_invites (
  id CHAR(36) PK, server_id -> servers ON DELETE CASCADE,
  code VARCHAR(32) NOT NULL UNIQUE,
  created_by CHAR(36) NOT NULL,
  max_uses INT NULL, uses INT NOT NULL DEFAULT 0,
  expires_at DATETIME(3) NULL, revoked_at DATETIME(3) NULL,
  created_at
)

-- Optional phase-2: per-channel permission overwrites
server_channel_overwrites (
  id PK, channel_id -> server_channels ON DELETE CASCADE,
  role_id CHAR(36) NULL, member_id CHAR(36) NULL,   -- exactly one set
  allow JSON NOT NULL, deny JSON NOT NULL,
  UNIQUE keyed appropriately
)
```

**Permissions:** JSON object per role, fixed key set for 1.3.0:
`view_channel, send_messages, attach_files, add_reactions, create_poll, embed_links, mention_everyone, manage_messages, manage_channels, manage_roles, kick_members, ban_members, manage_nicknames, manage_server`
(JSON over Discord's 53-bit integer — readable, plenty fast at this scale; can migrate to bitmask later without API changes.) `ADMINISTRATOR`-equivalent: `manage_server` + all others? Discord has a dedicated Administrator flag — add `administrator BOOL` to `server_roles` that bypasses all checks. Default `@everyone` role gets sensible defaults (`view_channel`, `send_messages`, `attach_files`, `add_reactions`, `create_poll`, `embed_links`).

**Permission resolution** (port Discord's algorithm into a shared helper, e.g. `server/permissions.mjs`):

```
base = union(allow) of all member's roles' permissions
if any role has administrator → all permissions
channel_overwrites (if implemented):
  apply @everyone deny → @everyone allow
  apply summed role denies → summed role allows   (allow wins over deny across roles)
  apply member deny → member allow
flags: view_channel && !timed_out for send_messages etc.
```

### Backend

**New RPCs in `server/rpc.mjs`** (mutations transactional; permission-checked via helper):

- `create_server(name, description?, icon_url?)` → server + `@everyone` role (is_default, position 0) + optional template seeding (`#general` + `#announcements`-style channels; creator gets a `Server Creator`-ish role or just @everyone+owner flag — Discord gives owner all perms implicitly; model: `servers.owner_id` bypasses permission checks) + owner `server_members` row + mirrored `conversation_members` for each channel.
- `get_my_servers()` → rail data: id, name, icon_url, owner flag, per-server unread/mention aggregates.
- `get_server_view(server_id)` → **one round-trip payload** for the whole server UI: server row, categories, channels (each with `conversation_id`, my effective permissions, unread count, mention count), roles (ordered), members (id, profile fields, nickname, highest role, joined_at), my membership. This is the hot path — keep it to ~5 queries.
- `update_server`, `delete_server` (owner), `leave_server` (removes `server_members` + all mirrored `conversation_members` rows across channels), `kick_member`, `set_member_role`, `set_member_nickname`, `timeout_member` (optional).
- Channel CRUD: `create_channel`, `update_channel` (name/topic/slow_mode/readonly/category/position), `delete_channel`, `reorder_channels`.
- Category CRUD: `create_category`, `update_category`, `delete_category` (channels → uncategorized).
- Role CRUD: `create_role`, `update_role` (name/color/hoist/mentionable/permissions/position), `delete_role` (reassign members to @everyone), `reorder_roles`. Enforce Discord's rules: can't edit @everyone's name; can't grant permissions you lack; can't touch roles ≥ your highest.
- Invites: `create_invite(server_id, {max_uses, expires_in_hours})` → `{ code }`; `join_server_by_code(code)` → validate expiry/uses/revocation → insert `server_members` (@everyone) + mirror `conversation_members` into **every text channel** + `uses++`; `list_invites`, `revoke_invite`. Vanity codes deferred.
- `set_channel_overwrite` / `remove_channel_overwrite` — only if per-channel overwrites ship in 1.3.0 (§10).

**Integration points (the risky part — budget time):**

- `data.mjs`:
  - `TABLES` allowlist += all `server_*` tables.
  - `policy()`: new tables get read policies scoped to server members (`EXISTS server_members`) and **no write policies** — all mutations via RPC. `conversations`/`conversation_members`/`messages` policies gain `kind='server'` branches as described in §3-core.
  - `canInsert('messages')`: for `kind='server'` → check `send_messages` permission + `view_channel` + `!is_readonly` (unless `manage_messages`) + slow-mode (last message by sender in channel < `slow_mode_seconds`) + verification level (account age) + `timed_out_until`. Keep DM block-check for `kind='dm'`/`'group'`.
  - `canInsert('message_reactions'|'poll_votes'|...)`: server channels inherit membership via mirror — reactions/polls need `add_reactions`/`create_poll` checks optionally (phase 2; membership check suffices for 1.3.0 since mirror covers it).
  - `canInsert('conversation_members')` / `policy update/delete`: deny when the conversation `kind='server'`.
  - `protectedByTable`: server tables are RPC-only so mostly N/A; add `conversations.kind` to protected columns (can't be changed via API).
  - `realtimeColumns` list (delete path): add `server_id`, `role_id`, `channel_id`-ish keys.
- `rpc.mjs userGroupList`: exclude `kind='server'`.
- `realtime.mjs`:
  - `SAFE_KEYS` += `server_id`, `role_id`, `category_id`, `channel_id`, `code`(? — invite codes shouldn't leak in keys; use `id` only for invites).
  - `recipientsFor`: cases for `servers`, `server_members`, `server_roles`, `server_categories`, `server_channels`, `server_invites` → resolve members via `server_members` (add a `serverMembers()` lookup parallel to `conversationMembers()`, Redis-cached 20 s like the existing one).
  - `RPC_CHANGES`: add entries for every new RPC so clients refresh (`create_server`, `join_server_by_code`, `create_channel`, `update_channel`, `delete_channel`, channel/member/role/invite mutations). Alternative: emit a synthetic `server_meta` change per server — simpler to just map each RPC to its table changes.
- `notifications.mjs`: **`notifyNewMessage` maps `messages`→'dm' mode today** — server channel messages would wrongly use DM templates/prefs. Detect `kind='server'` (join `conversations`+`server_channels` once per message) and either (a) treat as new `server` channel with its own `notification_preferences` columns (`server_mode` etc. — schema add), or (b) reuse `dm_*` prefs for 1.3.0 and add a `servers` section in NotificationSettings later. `conversation_members.muted` already suppresses per-channel — **channel mute works for free** (big synergy with 1.2.5). Mention overrides: `@everyone`/role mentions should bypass mode — extend `mentionsUser` checks. FCM `data` payload already carries `conversation_id` → push deep-links to channels work once routing supports it.
- `encryption.mjs`: `messages.content` encryption is table-based — server channels inherit free. Global-chat admin visibility does NOT extend to servers (private by design — see §10).
- `mediaUrl.ts`/storage: chat media paths are `<userId>/<conversation_id>/...` — server channels are conversation ids → signing/membership checks already work via `conversation_members` mirror. Server icons need a **public** read path (icons aren't sensitive): new bucket `server-icons` (public) or signed like chat media — public bucket is simpler; create via Supabase dashboard/config, document in docs.
- `import-postgres.mjs`: add new tables to the import list if the PG migration path must carry them.

## 6. Risks & gotchas

- **`ChatView.tsx` is ~3000 lines** — the biggest regression risk. Keep changes surgical: add `kind` prop/context, extract message-row rendering into a component during grouping work, don't rewrite fetch/realtime logic (`messageFetch.ts`, `messageRealtime.ts`, `reconcileMessage.ts` are well-factored — reuse).
- **`data.mjs` policy/canInsert is the security boundary** — every new table needs an explicit policy decision; server-channel message inserts are the highest-risk path (permission bypass = spam in private channels). Server-side tests required.
- **Membership mirroring drift** — `server_members` ↔ `conversation_members` must stay consistent or realtime recipients/notifications/media-signing break. All writes in transactions; add a consistency check script or test.
- **`get_user_group_list`/sidebar pollution** — forgetting the `kind='server'` exclusion floods the Groups section (called out in §3).
- **Notifications channel mapping** — server messages currently fall into 'dm' prefs; fix before launch or users get wrong templates.
- **localStorage cache** — new cache namespaces; don't break `veyra-cache:v2:` readers.
- **Serverless cold starts** — `get_server_view`/`get_my_servers` hit MariaDB directly (no Redis read cache for RPCs today — `cachedRead` only wraps `/api/data` selects; consider caching `get_my_servers` briefly or accept the cost).
- **Supabase Storage buckets** — `server-icons` public bucket must be created in the Supabase project (manual step — document in README/docs; can't be created from code).
- **Mention tokens** — mixing `@username` text and `<@&id>` tokens needs `MessageMarkdown` + `mentions.ts` + notification regexes all updated consistently.

## 9. Decisions made in this plan (confirm or override)

- Channels reuse `conversations` (`kind='server'`) with mirrored `conversation_members`.
- Permissions as JSON booleans (not Discord's bitmask) + `administrator` flag.
- Per-channel permission overwrites: **phase 2** — 1.3.0 ships role-level permissions + `is_readonly`/`slow_mode`/`timed_out`/`verification_level` channel flags. (Discord purists may want overwrites day one — it's the most complex piece; recommend deferring.)
- Kick only (no ban list) for 1.3.0.
- Group DMs keep Veyra's friendship-required adds and owner/admin roles (safer than Discord's anyone-can-add); revisit if user wants exact parity.
- DM history survives unfriend (Discord keeps channels until deleted); unfriended users drop out of the friends list. **Confirm** — alternative is deleting the DM for the unfriender.
- Discord dark palette becomes the default dark theme; light theme kept.
- Structured mention tokens for roles/channels; `@username`/`@everyone` text stays for users.
